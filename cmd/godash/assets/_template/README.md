# godash starter

A minimal Flutter + Go/TinyGo project template powered by [godash](https://github.com/nosuta/godash).

## What is included

- A single `EchoService` RPC example using godash's Bridge/Transport
- A `CounterService` demo that persists a number in SQLite (`go/rpc/entrypoint.go`
  opens the database godash hands to `EntryPoint`)
- Protobuf code generation wired to godash's custom generators
- The `native_internal` Flutter plugin for native FFI, materialised into
  `.godash/native_internal` by the CLI

## What is NOT included (you own these)

- `lib/main.dart` — your UI
- `proto/*.proto` — your services (all files are compiled, not just `echo.proto`)
- `go/rpc/*_server.go` — your handler implementations (structs named
  `<Service>Server` that implement the generated `<Service>RPCHandler` interfaces)
- `go/rpc/entrypoint.go` — your app init. The template ships one that opens the
  SQLite database; godash only writes a no-op default when the file is missing,
  so your edits are preserved.
- `pubspec.yaml`, `go.mod` — your dependencies and module name
- `core.env` — your NDK path, lib name, etc.

Everything else (the `main*.go` wiring, the RPC dispatch, the web worker
template, the TinyGo `wasm_exec.js`, the licenses template, the native
bridge plugin) is owned by godash and regenerated/extracted on every
`godash prepare` or build.

## SQLite persistence

`go/rpc/entrypoint.go` opens the per-install database with
`sqlite.Open(databasePath)` and creates the `counters` table. `CounterServer`
reads and updates it, and `lib/main.dart` shows a button that increments the
stored value. The value survives native app restarts and web page reloads
(OPFS). `database/sql` is used as usual; godash picks the driver:

- native: `modernc.org/sqlite` (pure Go, no cgo)
- web: `github.com/nosuta/go-wasmsqlite` + OPFS

The web worker needs `web/sqlite3.js` and `web/sqlite3.wasm`; `godash web run`
and `godash web build` download them automatically when missing. OPFS also
requires cross-origin isolation, so `godash web run` sends the COOP/COEP
headers (`web/_headers` does the same for production hosting).

## Build with the `godash` CLI

The `godash` CLI replaces the legacy Makefile and is the single entry point
for everything:

```sh
# Verify required tools are installed
godash doctor

# Initialise / regenerate derived files
godash prepare

# Build for each target
godash web build                   # Web release
godash web run                     # Web dev server
godash android apk                 # Android APK
godash ios                         # iOS .app
godash macos build                 # macOS .app
godash macos run                   # Run macOS app

# Clean build artifacts
godash clean
godash reset                       # also remove generated platform dirs

# Pull in new godash changes
godash upgrade
```

Run `godash help` (or `godash help <subcommand>`) for the full reference.

## How the package boundary works

The template does NOT vendor any godash source. Instead:

- `pubspec.yaml` depends on `godash: ^2.2.7` (from pub.dev) and on
  `native_internal: path: .godash/native_internal` (materialised by the CLI).
- `go.mod` requires `github.com/nosuta/godash/v2` with no `replace`; the
  module resolves from the Go module cache.
- On every `godash prepare` (and every build), godash:
  - resolves the godash source directory from the project's Go module graph
    (`$GODASH_MODULE_DIR`),
  - extracts the web platform assets (index.html, worker.js, …) from
    embedded data into `<project>/web/`,
  - regenerates `go/main*.go`, `go/rpc/rpc_handler.go` and
    `go/rpc/hot_handler.go` from the discovered services in
    `go/pb/*.godash.go`,
  - runs `go-licenses` to produce `lib/licenses/licenses.g.dart`,
  - copies the `native_internal` plugin shell into `.godash/native_internal`
    and builds the Go native library for the target platform into it.

No local godash checkout is required. Path-replace projects (local
development or a fork) still work: the CLI provisions the declared checkout
automatically if it is missing. Override the source with `GODASH_REPO` /
`GODASH_REF`, or set `GODASH_NO_PROVISION=1` to manage it yourself.

This means **there is no template-level merge on upgrade**. To pick up
new godash releases, run `godash upgrade`.

## Generating a new project from this template

Use the `godash` CLI:

```sh
# Install godash
go install github.com/nosuta/godash/v2/cmd/godash@latest

# Create a new project (interactive)
godash
```

The template is embedded in the CLI, so `godash new` works offline and is
version-locked to the installed godash. To scaffold from a custom local or
remote template instead, set `GODASH_TEMPLATE`:

```sh
GODASH_TEMPLATE=/path/to/custom/template godash
GODASH_TEMPLATE=https://github.com/you/your-template godash
```

## Upgrading godash

```sh
godash upgrade
```

For this template (a version-pinned project), `godash upgrade` runs
`flutter pub upgrade godash native_internal` and `go get -u
github.com/nosuta/godash/v2`, then re-runs `godash prepare` to regenerate
derived files and refresh `.godash/native_internal`.

For path-replace projects (local development or a fork), it runs `git pull`
in the declared godash checkout instead of the package upgrades.
